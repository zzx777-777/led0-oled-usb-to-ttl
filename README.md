## 三、程序结构

主循环中顺序调用四个任务，均不阻塞：

```c
while (1)
{
  Key_Task();      /* 扫描按键 → 改状态 */
  Packet_Task();   /* 拆包校验 → 改状态 */
  LED_Task();      /* 到时间 → 换灯    */
  UI_Task();       /* 状态变了 → 刷屏  */
}
```

所有模块共用一份运行状态（唯一数据源），按键与串口**只改状态**，LED / OLED / 串口反馈**只读状态**：

```c
typedef struct __attribute__((packed)) {
  uint8_t  header;    /* 0xAA            */
  uint8_t  run;       /* 00 暂停 / 01 运行 */
  uint8_t  dir;       /* 00 正向 / 01 反向 */
  uint16_t step_ms;   /* 小端：低字节在前  */
  uint8_t  check;     /* 前 5 字节和低 8 位 */
} Packet;
```

运行状态变量：`g_run`（运行/暂停）、`g_dir`（方向）、`g_step`（间隔 ms）、`g_led`（当前灯号）、`g_dirty`（需刷新显示）。

**中断原则**：中断回调只做数据搬运和置标志（接收回调置 `pkt_ready`、发送完成回调清 `fb_busy`），校验、解析、状态更新、OLED 刷新全部放在主循环，符合作业第二章第 2 条要求。

## 四、串口数据包协议

每包 6 字节，固定长度：

| 字节 | 字段     | 取值              | 说明                                   |
| -- | ------ | --------------- | ------------------------------------ |
| 1  | 帧头     | `0xAA`          | 固定                                   |
| 2  | RUN    | `0x00` / `0x01` | 暂停 / 运行                              |
| 3  | DIR    | `0x00` / `0x01` | 正向 / 反向                              |
| 4  | STEP_L | `0x00~0xFF`     | 间隔低字节（先发）                            |
| 5  | STEP_H | `0x00~0xFF`     | 间隔高字节（后发）                            |
| 6  | CHECK  | `0x00~0xFF`     | `(0xAA+RUN+DIR+STEP_L+STEP_H) % 256` |

接收流程：中断收满 6 字节 → 回调置 `pkt_ready` → 主循环中依次判断 **帧头 / 校验和 / RUN、DIR 是否只为 0、1 / 间隔是否在 100~2000ms**，任一不满足则整包丢弃，不修改任何状态。

示例：`AA 01 00 2C 01 D8` = 运行、正向、300 ms（`0x012C`）。

## 五、串口反馈格式（自定义）

每 30 个字符以内、单行、英文，便于串口助手直接阅读，格式如下：

```
STATE=RUN,DIR=FWD,STEP=300,LED=1
```

| 字段      | 含义           | 取值示例             |
| ------- | ------------ | ---------------- |
| `STATE` | 运行状态         | `RUN` / `STOP`   |
| `DIR`   | 流水方向         | `FWD` / `REV`    |
| `STEP`  | 相邻 LED 切换间隔  | 单位 ms，`100~2000` |
| `LED`   | 当前点亮的 LED 编号 | `1 / 2 / 3`      |

- 每个字段 `键=值`，字段之间用英文逗号分隔，行尾 `\r\n`；
- 发送时机：上电一次、收到合法数据包后、按键改变运行状态或方向后；
- 实现方式：`snprintf` 格式化到静态缓冲区，再由 `HAL_UART_Transmit_IT()` 启动中断发送（发送结束前缓冲区不可改写）。

## 六、关键实现说明

**1. 非阻塞定时**：流水灯用时间戳比较判断，而不是 `HAL_Delay`：

```c
if (HAL_GetTick() - g_last < g_step) return;
g_last = HAL_GetTick();
```

主循环一直在跑，因此间隔设为 2000 ms 时，按键和串口依然能立即响应。

**2. 按键消抖 + 单次触发**：不调用延时函数，而是记录原始电平与变化时刻，电平保持 15 ms 不变才确认为一次有效变化；只在“稳定为低”的瞬间返回一次，因此按住不放不会连续触发。

**3. 串口接收**：`HAL_UART_Receive_IT(&huart1, &rx_pkt, 6)` 收满 6 字节触发回调；主循环处理完一包后重新启动接收。作业要求“电脑每次发一包、收到反馈后再发下一包”，与该机制匹配。

**4. OLED 显示**：状态改变时置 `g_dirty`，`UI_Task()` 检测到才刷新，避免每轮循环都刷屏拖慢流水灯；每行末尾补 3 个空格，用于擦除上一次更长的内容。

## 十一、思考题

> 当流水灯的切换间隔较长时（如 2000 ms），有没有出现按下按键和发送串口指令时不能立刻执行，会有一定的延迟？如果有，思考问题出在哪里，可以怎样改进？

**会延迟的写法**（本作业未采用）：

```c
HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_0);
HAL_Delay(2000);          /* 这 2 秒里 CPU 停在原地 */
```

`HAL_Delay()` 是阻塞式等待：它让 CPU 空转直到延时结束，期间主循环不再执行下一轮，按键扫描和串口数据包处理都被跳过。间隔设为 2000 ms 时，按键最多要等 2 秒才有响应；串口数据虽然能靠中断收下，但拆包处理同样要等延时结束，表现为“发完包灯过一会儿才变”。

**本作业的改进**：

1. **用时间戳代替延时**：`LED_Task()` 每次只判断 `HAL_GetTick() - g_last >= g_step`，不满足就立即返回，主循环继续转。无论间隔设成 100 ms 还是 2000 ms，主循环每圈的耗时都是一样的（几十微秒），按键和串口都能及时响应。
2. **中断只做搬运**：串口接收在中断里完成，即使主循环某一刻稍慢，数据也已经存进缓冲区，不会丢。
3. **显示按需刷新**：OLED 只在状态变化时刷（`g_dirty`），避免刷屏这几毫秒反过来拖慢按键响应。

如果确实需要在延时期间也响应事件，除了上述“状态机 + 时间戳”写法，另一种思路是把定时任务交给硬件定时器中断，但那样同样要求中断里不做耗时操作。核心结论是：**任何长于主循环周期的 `HAL_Delay()` 都会破坏实时性，应尽量用“查询时间 + 立即返回”的方式替代。**
